# 规模测算与英文分卷方案

> 本文的数字都是**实测**得来（2026-09-13），不是估算。原始记录见 [06-verification.md](06-verification.md)。

## 1. 实测结果

| 目标 | 条目数 | 正文 HTML | 未压缩正文 | **MOBI** | 正文记录数 | 记录占用 |
| --- | --- | --- | --- | --- | --- | --- |
| 样例（冒烟） | 9 | 2.1 KB | — | 12.6 KB | — | — |
| 中文全量（DBpedia 源） | 1,124,787 | 558.9 MB | 514.7 MB | 317.1 MB | 62,833 | 95.9% |
| **中文全量（官方 dump 源）** | **1,284,543** | 572.4 MB | **435.8 MB** | **304 MB** | **53,203** | **81.2%** |
| 英文小样 | 200,000 | 97.9 MB | 84.6 MB | 45.3 MB | 20,660 | 31.5% |
| 英文全量（DBpedia 摘要，筛选后） | **5,975,823** | — | — | 单本装不下 | 预估 23 万～70 万 | 超限 |

单条常量（用于外推）：

| 语言 / 来源 | 每条的正文字节 | 每条的 MOBI 字节 | 每条的记录数 |
| --- | --- | --- | --- |
| 中文（DBpedia 摘要） | 457.6 B | 277.4 B | 0.0559 |
| 中文（官方 dump 首段） | 339.3 B | 248.0 B | **0.0414** |
| 英文（DBpedia 摘要） | 423.1 B | 237.7 B | **0.1033** |

两个反直觉的事实：

- **官方 dump 源的条目更多（128 万 vs 112 万），产物体积反而更小（304 MB vs 317 MB）。**
  因为维基首段比 DBpedia 摘要短，而且清洗后过滤掉了过短的条目。
- **英文单条比中文贵一倍以上**（0.1033 vs 0.0414 条记录/条）。这是后面英文必须分卷的直接原因。

## 2. 关键发现：瓶颈是 PalmDB 记录数，不是体积

MOBI 的 PalmDB 头里记录数是 **16 位**，硬上限 **65,535** 条（正文 + 图像 + 索引合计）。

中文全量（官方 dump 源）实测：

```
palmdb.rec_count            = 54166      ← 总记录数（82.7%）
palmdoc.text_record_count   = 53203      ← 仅正文
mobi.orth_index             = 53204      ← 索引入口
```

### 记录数怎么算

```
正文记录数 ≈ 未压缩正文字节 ÷ 8192
```

两种来源都精确符合这条式子。**注意：这里的"未压缩正文"远小于你看到的 HTML 体积**——
`idx:entry` / `idx:orth` / `mbp:pagebreak` 这些标记会被编译器消费进索引，**不占正文记录**。
所以不能拿 HTML 大小去估记录数（会高估约 40%，我据此误判过一次）。

### 单本 MOBI 的条目上限

| 语言 / 来源 | 单本条数上限 = 65,535 ÷ 每条记录数 |
| --- | --- |
| 中文（官方 dump 首段） | **约 158 万条** |
| 中文（DBpedia 摘要） | 约 117 万条 |
| 英文（DBpedia 摘要） | **约 63 万条** |

由此得出两个结论：

1. **中文全量（128 万条）单本装得下**，还剩约 18% 记录余量。
2. **英文全量（约 690 万条）单本结构上不可行**，需要分卷（见 §3）。

### 顺带纠正一个经验值

"Kindle 词典别超过 280 MB"这个说法**不足以判断能否装下**：中文官方 dump 源做到了 304 MB / 128 万条
而记录数只用了 81%；但换一本释义更长、条目更多的词典，可能体积才 300 MB 出头就先撞记录上限。
**判断依据应该是记录数，不是体积。**

## 3. 英文的实测分布与缩减方案

**实测（2026-09-14，DBpedia short-abstracts 全量，与中文同口径过滤后）：**

```
条目数   5,975,823
等价 TSV 2.05 GB
平均      367 B/条
```

单本上限 65,535 条记录。**英文的系数还没在全量尺度上实测过**（只有 20 万条样本的 3335；
而中文的经验是尺度变大后系数会翻倍，3200 → 6936）。所以下表给出**乐观 / 保守**两个估计：

### 一、按重要度筛条目（释义越长通常越重要）

| 释义阈值 | 保留条数 | 占比 | TSV | 预估记录（乐观 / 保守） |
| --- | --- | --- | --- | --- |
| ≥200 B | 4,251,645 | 71.1% | 1.91 GB | 614,815 / 280,878 |
| ≥300 B | 3,140,034 | 52.5% | 1.60 GB | 515,355 / 235,440 |
| ≥400 B | 2,219,021 | 37.1% | 1.26 GB | 405,316 / 185,168 |
| ≥500 B | 1,410,514 | 23.6% | 0.88 GB | 284,213 / 129,842 |
| ≥700 B | 330,589 | 5.5% | 0.26 GB | 82,496 / 37,688 |

### 二、截断释义（条目数不变）

| 截断到 | TSV | 预估记录（乐观 / 保守） |
| --- | --- | --- |
| 250 B | 1.47 GB | 473,137 / 216,152 |
| 180 B | 1.20 GB | 387,430 / 176,997 |
| 120 B | 0.93 GB | 299,228 / 136,702 |
| 80 B | 0.72 GB | 232,172 / 106,068 |

### 结论：**单靠截断装不下**

即使把释义砍到 80 字节、条目一条不删，预估仍是 23 万 / 10.6 万条记录——**远超 65,535**。
换算回可用容量：

| 情形 | 单本可容纳条目数 |
| --- | --- |
| 释义截到 250 B | 约 **73 万（乐观）～ 160 万（保守）** |

也就是说要从 598 万条里**选出 12%～27%**。

### 该用"重要度"而不是"释义长度"来选

**释义长度只是粗代理**（长摘要 ≈ 重要条目）。真正该用的是**跨语言链接数**——
一个条目有多少个其他语言版本。英维 6.9M 条 vs 中维 1.4M 条的差异正体现在这里。

**实测（2026-09-14，`enwiki-latest-langlinks.sql.gz` + `enwiki-latest-page.sql.gz`）：**

```
langlinks  47,861,426 条链接，覆盖 7,301,108 个页面
page       扫描 66,194,556 行
输出       4,050,920 条（ns0 且语言数 ≥ 2）   用时 5 分 51 秒
```

语言数分布（取阈值 → 保留条数）：

| 语言数 ≥ | 保留条数 | 占比 |
| --- | --- | --- |
| ≥30 | 203,171 | 5.0% |
| ≥20 | 389,109 | 9.6% |
| ≥15 | 574,940 | 14.2% |
| ≥12 | 771,335 | 19.0% |
| **≥10** | **969,714** | **23.9%** |
| ≥9 | 1,106,664 | 27.3% |
| ≥8 | 1,287,400 | 31.8% |
| ≥7 | 1,505,880 | 37.2% |
| ≥5 | 2,133,835 | 52.7% |
| ≥2 | 4,050,920 | 100.0% |

**注意：只有 405 万条有 ≥2 个语言版本**——另外 290 万条（冷门物种、赛事、小地名等）
在"显著度"这个维度上本来就该被淘汰。

**推荐档位：「语言数 ≥ 10」→ 969,714 条**，正好落在单本容量估算区间的中部。
这个门槛比"按释义长度筛"有道理得多：有 10 种以上语言版本的条目，几乎都是读者真会去查的。

### 组合方案（推荐）

```
enwiki 官方 dump（690 万条）
  → 解析出词表 + 重定向异名
  → 按「跨语言链接数 ≥ 10」筛到 97 万条
  → 释义截断到 250 B（可选，若实测系数偏保守再加）
  → 单本 .mobi
```

### 必须先做的一次实测

英文系数在全量尺度上是未知数。**建议先跑 100 万条实测**，用真实记录数定系数，再决定最终档位——
盲目按乐观系数选到 160 万条、结果撞上限，会白做一遍。

```bash
# 先取 100 万条实测系数（工具的 --sample 是抽样页数，这里更适合先切一份 TSV）
python scripts/wiki2kindle.py data/short-abstracts_lang=en.ttl.bz2 --sample 200000
```

## 4. 分卷是否可行（仍待真机验证）

如果不想减条目，就得把英文拆成多卷（按上面数字，约需 3～9 卷）。**但前提是 Kindle 在同一语言下
装多本词典时，默认词典查不到会继续查非默认词典**——这条只能真机验证：

侧载两本自制英文词典，只把其中一本设为默认，用只存在于另一本里的词测试。

**若 Kindle 不回退查询 → 分卷不可用 → 只能减条目**（即上面的方案）。
**若会回退 → 分卷可用**，但要权衡：每卷更小、查词要跨多本索引，速度会受影响。

## 5. 中文的余量

中文全量（官方 dump 源）128 万条 / 上限约 158 万条，**还剩约 18% 余量**。

- **可以再放，但别再大幅加内容**：给释义加信息框字段、把首段换成长摘要，都会推高记录数。
- 加入重定向异名**不增加正文记录**（异名只进索引）——实测 130 万条异名只让 INDX 从 416 条涨到 959 条，
  再叠加 5.3 万条归一别名共 **974 条**，正文记录数**逐字节不变**。相对 65,535 仍有充足余量。
- 若要再多收条目（例如把因"首段过短"被过滤的 17.5 万条也纳入），离上限还有约 30 万条的空间。
- 反过来看：**异名是"免费"的信息增量**，而释义长度是"昂贵"的。想提升查得率，优先扩异名表。
